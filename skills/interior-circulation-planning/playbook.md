# 动线规划执行 Playbook

## 1. 确定审计对象

一次审计只绑定一个 `floorplanId`、一个冻结 handoff 和一个当前原生模型哈希。用户没有指定后端时，沿用已经完成建模的后端，不能为了方便切到 HTML 代理模型。

## 2. 先核对三层事实

按顺序打开并并排检查：

1. 原始户型图：看到真实墙、门洞、窗、空间和源对象。
2. 平面规划叠图：红墙、开口和组件描线必须覆盖原图对应证据。
3. 原生模型顶视图：墙门窗与平面规划一致，组件方向和位置与当前布局状态一致。

任一层不一致，分类为 `input-integrity`，不进入动线计算。

## 3. 建立两张自由空间图

### 结构基线图

只包含楼板、红墙、真实开口和房间多边形。它不代表推荐规范，只记录原户型能力。

### 当前布局图

复制结构基线图，再加入当前落地家具、柜体和设备的精确轮廓。吊灯、挂画、镜子、地毯等不阻塞平面行走，但可由其他 Skill 检查高度或使用关系。

## 4. 路线集合

算法自动生成三种路线：

- `portal-crossing`：门洞两侧是否能穿过。
- `entry-to-room`：从任一外部入口到房间内部稳定锚点。
- `through-room`：同一房间多个开口之间是否能穿行。

一个房间只有一个入口不是硬编码要求。结构开口数完全继承原图；本 Skill只检查当前摆放是否让既有开口失效。

## 5. 判定责任

| 结构基线 | 当前布局 | 责任 |
|---|---|---|
| 达到目标 | 低于目标 | 当前布局 |
| 低于目标 | 保持基线 | 原户型限制 |
| 低于目标 | 继续变窄 | 当前布局 |
| 不可达 | 仍不可达 | 原户型限制 |
| 可达 | 不可达 | 当前布局 |

报告同时保留原值、现值、差值和有效要求，禁止只写“通过/不通过”。

## 6. 调整循环

1. 先看反事实归因，优先处理单独移除即可恢复的组件。
2. 运行 adjustment planner；算法按路线恢复、贴墙、面向、移动量、旋转量和稳定 ID
   选择唯一操作，Agent 不再从候选中主观挑选。
3. 当前建模后端校验计划摘要并直接执行该可逆变换，不向用户确认；本 Skill 不直接写原生文件。
4. 导出新的布局状态和原生模型哈希。
5. 原 audit 作废，从头重跑全部路线；把前一计划作为停滞检测输入。失败向量未严格改善即停止。

不得通过缩小源对象、删除原图对象、跨房间移动或修改红墙来消除告警。
确定性安全修正不是设计决策，不询问用户；只有算法无解、事实冲突、用户硬性要求缺失或
不可逆/付费/公开动作才把所有阻塞合并成一次问题。

## 7. 视觉终审

Agent 逐项记录：

- 原图到平面规划是否一致。
- 平面规划到当前模型结构是否一致。
- 所有落地障碍轮廓、方向和房间归属是否一致。
- 每个门洞与连接是否一致。
- 每条计算路线是否已查看。
- 原户型限制是否仅提示而未阻断。

只有代码审计和视觉复核同时接受，才能写最终 result。

## 8. 下游交接

最终 result 必须绑定同一 `nativeModelSha256`。找机位时模型哈希变化，必须重做动线审计，不能用旧 result 放行。
