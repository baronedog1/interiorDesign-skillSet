# 平面布局规划

输入原图、标注尺寸和用户意图；输出 `layout.json` 给 HTML 建模。按需生成原生平面方案图片，图片不是测量事实源。

空白/毛坯户型图、看不出偏好，或现有资料不能确定居住与布局意图时，先按[需求访谈](playbook/requirements-interview.md)分轮询问。先读已有对话，不重复索要答案；有家具的图也不等于用户认可其布局。把确认、待定、推测与用户授权自由发挥分开记录到 `requirements.json`；有实质冲突先讲清取舍，再规划受影响区域。用户暂未回复时可继续读结构和校准，不自行把假设写成已确认需求。

读 [规划方法](playbook.md)，字段唯一来源是 [布局合同](../interior-html-modeling/data_contract.md)。命令入口 [scripts/run.py](scripts/run.py)：`handoff INPUT --out layout.json`、`observe INPUT --out observations.json`；显式按宿主墙生成家具锚点用 `anchor INPUT --id ID --wall-id WALL --offset 米 --gap 米 --out layout.json`。共享确定性引擎由 HTML Skill 维护，不复制另一套几何字段。

访谈后 `handoff INPUT --requirements requirements.json --out layout.json` 同交付 `layout.requirements.json`；后续命令会发现输入布局旁的同名需求侧车。脚本只保留/核对交接数据，不替 Agent 提问、不按问卷填满率决定是否能设计。HTML建模先读该需求文件，把约束落实到房间、家具锚点与CMF；下游不另猜一套偏好。

床默认床头靠真实墙；沙发按房间和阳台关系确定靠墙或开放放置；不是随便找最近墙。动线在布局生成前考虑，观察结果不能代替源规则。保留带问题草稿并修正源头，不凭格式通过宣称设计正确。

资产查询或平台交付调用 `idk-canvas-ingest-agent`。不得把平台 Key 放到布局、HTML 或报告。

人读 [PDF](SKILL_MANUAL.pdf)，详细执行见 [运行说明](local_runtime.md)。

每一步必须记录开始、完成、耗时及状态，遵循[统一时间合同](../interior-html-modeling/playbook/timing.md)；正式命令自动记录，读图、识图、原生调用与交付等待随执行登记，不事后补时间。

规划大件时先建立“需求→功能→组件→真实位置”的理由；开放功能区不自动生成书架/屏风隔断。详见playbook的功能选型方法，交接前看全屋顶视和开放区关系。

本轮统一规则见 [空间连接与完整构图](../interior-html-modeling/playbook/space-connections.md)：规划先确认空间连接；HTML按真实门型/状态装配；正视主图带到天花与地面；渲染保留本机位可见空间身份，不把阳台画成房间。

描线时区分真实连接与源缺口。同一接点用共享坐标；存在采样偏差时给出有源依据的 wallJoins，不以距离接近推断连接。handoff 与 HTML 使用同一模型内核，规则见 [墙角与源事实](../interior-html-modeling/playbook/editor-model.md)。

## playbook.md

# 从原图到家具锚点

先读已有需求，按[需求访谈](playbook/requirements-interview.md)识别缺失偏好并分轮补问，形成当前项目requirements记录。确认需求与图纸事实分开；只有结构可先独立还原，不能从空白图猜家庭人数和房间用途。后续功能区、家具容量、动线与风格应能追溯到需求或明确假设。

先识图，不把 OCR 文本、旧布局或图纸朝上当空间事实。保留原图，对尺寸标注、墙厚、门弧、窗和阳台边界分别辨认。脏图可由原生绘图清理成辅助参考，但不得让补画改变原始结构。用至少一条可信尺寸定标，其他已有尺寸交叉理解；无尺寸可做注明估算的概念稿，不能宣称精准。

统一米制、Y 向上、平面 x/z；图像 y 向下在入口转换一次，不镜像截图。共享墙只建一次；每个门窗引用真实宿主墙，offset 从 a 端量到开口起边。门开向、合页与门弧不清楚就保留来源疑问，不能猜成穿墙门板。开放客餐厅用真实开放连接，不补假墙。

先划定客厅、餐厅、卧室、厨卫、阳台等功能区，再标注主体 ID。房间名称和位置以图为准，不能把餐桌区猜成客厅。全户型一次整理共用墙、地、顶；不把一个房间孤立成另一套坐标。

家具生成前先选角色、真实尺寸、正面、使用空间。床的本地 -Z 为床头，+Z 为床尾；默认床头靠墙，避开门窗与衣柜开合。沙发背向支撑墙、面向电视或会客中心；阳台边应保留通路，可按需求选单人椅，不把多座沙发硬塞进窄走道。餐桌与椅子作为一个功能组，预留拉椅、落座和绕行空间。柜门、房门、抽屉的开合域要在放置前考虑；不把床垫、桌脚、地毯等合法组合接触误判为非法穿透。

`anchor` 根据宿主墙切向及朝房间的法向，直接计算家具中心与朝向：中心=墙 a+切向×(offset+家具宽/2)+内法向×(墙厚/2+家具深/2+gap)。正面=内法向；旋转角 atan2(nx,nz)。这是生成规则，不是下游看到穿模后挪家具。此命令只处理明确指定的对象，不自动替用户重排全屋；源图指定悬空布置时不调用靠墙算法。

生成 JSON 后读取 observations，并用识图对照原图检查全屋顶视关系。问题回到原图解释、坐标、宿主、组件朝向或选型规则，再生成；观察器不自动移动、隐藏、缩小对象。技术上不可解析或引用不存在才阻止该次编译，业务争议保留草稿和说明。

要多套平面方案时，宿主原生绘图附原图和已知尺度、不可变墙门窗、每套需求差异；逐张看图后将明确选择的布局转成 JSON。不能用代码画的标注图冒充原生绘图，也不能把图片像素当施工尺寸。

## 功能先于家具，开放区域不是隔断任务

开放书房首先是桌椅与使用空间，不自动等于新房间、屏风或书架。每件大件生成前先明确：服务哪个需求、是否重复已有功能、沿哪段真实可用墙或围绕哪个中心布置、占用哪些开合与通行空间。把选型理由与取舍简短记在需求记录，不新增打分门禁。

收纳结合真实可用墙面、现有柜体或书桌整合。只有确有分隔需求且通行、视线与尺度合适，才采用自由摆放的隔断；不能因客餐厅/书房相邻就沿功能边界排柜，也不照搬风格图里的书架。选组件先看功能、容量、尺寸和正面，再看款式；尺寸冲突回选型，不拉伸产品。

规划后看全屋顶视与开放区轴测，逐件解释大件为什么在这里。解释不成立就回需求解读或选型重做，不等渲染阶段隐藏。已认可布局保持不动，新增需求另存方案版本。

组件类别还不够：先分直排/贵妃位、餐桌人数和形状等结构家族，再选目录条目；sofa.straight与sofa.cloud不是仅颜色不同的同款。平台选品若改变结构家族，保留既有位置与空间需求，回布局选型后重新编译，不能压缩异形组件充当正确家具。

## 先确定空间如何连接

布局时把阳台/厨房等两端身份、门/移门/无门洞/固定玻璃、开合和玻璃性质写进opening源字段；窗的connects只代表视觉相邻，不参与通行。null外部不等于户外，补exteriorView来源。关键资料不明确按访谈补问，历史默认值明确是草稿。具体字段与消费者见 [空间连接与完整构图](../interior-html-modeling/playbook/space-connections.md)，不另维护连接旁表。


## playbook/plan-reading.md

# 从图面证据到空间与柜组

本方法负责如何读图和组织布局，不按图标命中数打分，不新增强校验、门禁或审批。

先将每段墙、洞口、固定烟道、上下柜轮廓与使用侧对应到原图。尺寸优先级是当前明确标注、用户确认、可靠比例估算；记录事实、推断和待确认。看不清会改变用途的符号时截取局部并标注位置询问；其余确定部分继续。不要凭房间用途加门窗，不以最新款式图推翻已确认平面。

厨房沿地柜/台面逐段追踪连接：一直线为一字；两相邻连续边为L；三边和两转角为U，短回转也算一边；相对两排但末端不连是双排。独立岛台四周有通行空间，半岛与主柜组连接，吧台是功能附加而非互斥几何类型。旋转与镜像不改变关系。台面在入口、冰箱和高柜处止边；独立岛台独立成组。

同一区域的线框可表示地柜、桌面、吊柜、灶具和烟机等不同高度，分别记录，不能只建最易认的一层。沿墙双X窄框、墙角折线井道都只是候选线索；结合图例、灶位、桌椅与用户说明确定。烟道、柱、管井、转角柜分清，固定设施占地不因柜宽改变。未知设备接口不虚构。

墙端用实际内/外完成面，不用中心线当柜端。原图为直角连续墙时按连接点与墙厚求交，不拼出假凹槽；斜角、台阶和真实空隙按源图保留。靠墙家具以真实背/侧面定位，保留安装、踢脚和设备净空；独立桌椅与岛台不推墙。先识别坐面、床头、柜门操作面，再按模型本地前向转换朝向。

定制柜先确定用途、可用整组宽、取物方向、固定盲段、门扇活动区，再分模块。上浅下深的双轮廓分别表达；不可用典型柜深覆盖源图的齐面关系。厨房、书房、儿童房和全屋调用相同的对象方法，不按房名限制规则复用。

榻榻米由连续床台、柜床关系和指定睡眠范围判断；枕头仅表示睡眠方向。普通床的明确标注优先。衣帽间先扣柜深求净通道，再安排开门、抽屉和椅子，不把总宽当净宽。图上无尺寸可注明概念估算，客户给过的已确认信息不重复问。

交接 layout.requirements.json 中记录 ruleSelections（对象/方法引用）、parameterOverrides（数值、归属、来源）、uncertainties（局部疑点）和当前 revision。它们是设计依据，不是问卷完成度或生成资格。构造落实到 HTML 的 [柜体与节点方法](../../interior-html-modeling/playbook/joinery.md)。


## playbook/requirements-interview.md

# 需求访谈：先理解怎么住，再决定怎么摆

## 何时进入

空白/毛坯图只有建筑信息，或原图、文字和历史对话不能说明居住方式、功能取舍、布局/风格偏好时，先开展访谈。图上既有家具、开发商样板布局、装饰颜色只能作为参考，不能自动当作用户选择。用户已有完整需求，只补真正缺失、互相矛盾或影响本次任务的信息；单纯描墙/测量不强行问装修风格。

先区分三件事：图上可核实的建筑事实、用户明确表达的偏好、Agent尚未证实的推测。结合任务范围列出会改变方案的未知量，按影响大小选择下一轮问题。不要先按某种风格摆好全屋，再让用户追认。

## 怎么问：分轮、有上下文、不是固定问卷

开头简短复述已知信息和为何需要补问。每轮只问便于一起回答的少量相关问题；先影响房间用途、容量和通路的事，再问细节，不一次发几十道题。用户可能一句话回答多个主题，应合并已有答案，不机械重复。根据回答继续追问，不规定轮数或“回答了几题才合格”。

优先了解这些影响布局的事项，再按实际生活情境展开：

- **谁住、怎么变化**：常住和偶住人数、孩子/长辈、宠物；客人留宿、未来家庭变化。只问功能需要，不索要姓名、身份证或诊断等无关隐私。行动、照护、无障碍需求用使用场景表达，不据年龄直接假设。
- **必须有什么、最在意什么**：卧室/床位、工作学习位、餐位、独立或共用空间；必须保留/不能接受的布置；功能冲突时优先保哪项。既有家具/设备是否保留，有无可核实尺寸与实物图。
- **日常如何使用**：做饭频率/油烟与厨电、在家办公/学习、看电视或会客、储物/囤货、家务清洁、洗烘晾晒；由生活习惯映射到具体空间和通路，不只问“喜欢什么风格”。
- **按回答追问相关空间**：常聚餐才细问常用/峰值餐位和餐边收纳；有居家办公才问同时使用人数、视频会议/安静需求；儿童空间问当前及可预见阶段；阳台问洗烘、晾晒、休闲的优先级。卧室问床尺寸/侧边通行/衣物收纳；厨房问开放意愿与真实条件；卫浴问干湿区与使用方式。没有相关需要不逐房重复审问。
- **边界与实施条件**：哪些结构/门窗/湿区不能动，图纸可信尺寸与不明项；对改动的意愿不等于结构改造许可。完整装修任务问预算的大致范围及包含硬装、家具、设备还是全部，工期/分期；不愿提供金额时用投入优先级，不把拒答当零预算。
- **风格与舒适偏好**：喜欢/不喜欢的颜色、木色、材料、明暗、触感、简洁程度，参考图具体喜欢哪部分；不只收一个风格名。不懂名称时给自然语言对比或带出处的参考图，让用户说喜恶；五种预设不是选择上限。风格暂不确定不妨碍先解决功能布局，也不能擅自定最终CMF。
- **方案和交付**：本次要布局讨论、几个取舍明确的备选，还是完整方案；图片/HTML/PDF依用户要求，未限定的完整方案仍默认高清图文PDF。不把每个任务升级成完整装修咨询。

可这样开始（根据已知事实删改，不照抄整套）：“这张图主要能看清墙和门窗，还看不出你们怎样住。我先了解三个会直接影响布局的事情：常住/偶住分别有哪些使用需要？哪些功能必须保留？现有家具或不能改的地方有哪些？”下一轮针对答复深入，例如“你说平时两人吃饭、周末六人聚餐，日常留大桌还是可伸缩桌更符合习惯？”不能把例子暗中当用户答案。

## 答复、冲突与何时进入规划

逐轮记录问题、答复来源、提问与收到答复的时间；等待用户的墙钟时间单列，不混进代码建模耗时。不要事后用修改时间补造答复时间。

收到答复后，用白话概括“必须满足、偏好、还没定”及其空间影响；关键取舍有歧义才请用户澄清，已经清楚的答案不再逐条要求批准。两条需求放不下/相互冲突时说明原因和选项，例如增加常驻书房会挤占哪一个客卧；不要悄悄删需求或靠压小家具满足。

未回复：保留当前提问和待定项，可继续读图、尺寸核对、不可变结构整理；不替用户决定依赖答案的房间用途。只缺不影响布局的颜色或装饰细节，可以先规划功能并留待后续。用户明确说“你决定/先出方案”，记录授权范围，给带假设的建议或对比方案，不将其标作用户明确选择。

当当前任务相关的使用需求和优先级已清楚，或用户已授权在明确假设下探索，就进入布局。不是要每一类问题都有答案，也不是百分比/评分/硬门禁。用户改需求时更新同一需求记录的revision和来源，定位受影响的房间、家具/CMF与下游输出；不覆盖无关已认可内容。

## 唯一需求记录与交接

文件只保存在当前项目C盘，不打包进Skill/Git。`requirements.json` 使用 `schema: interior.requirements/1`、`projectId`（等于layout.id）、`revision`（整数）、`updatedAt`（实际时间）、`scope`（本次任务）。

`items` 是灵活主题数组，每项含 `id`、`topic`、`value`、`status`、`source`；按需加 `priority`（must/prefer/optional）与 `affects`（房间/对象或设计影响）。status：`confirmed`用户明确表达，`tentative`Agent推测/待选，`unknown`未回答，`delegated`用户授权Agent决策；value未知用null，“无此需求/不喜欢”用明确否定，不把未知当否定。source写答复文字摘要及可用消息ID/资料位置，不虚构引用。

`openQuestions` 可保存问题与影响；`rounds` 可保存每轮问题、askedAt、answeredAt和答复来源。没有真实时间写null并说明，不造时间；不要求把完整私聊重复复制进此文件。

例：`{"id":"dining-capacity","topic":"餐厅","value":{"dailySeats":2,"guestSeats":6},"status":"confirmed","source":"用户本轮回答","priority":"must","affects":["dining"]}`。不懂风格：value为null/status为unknown；“请你推荐”应记录为delegated，不能编一个confirmed风格。

Agent负责提问、语义判断和把需求转成布局，脚本不替代对话。`handoff --requirements`核对schema/projectId/items基本结构后，将原需求完整复制为输出布局同名的 `.requirements.json`，打印路径与摘要。省略参数时自动沿用输入布局旁的同名侧车；没有需求文件的历史/纯描图流程仍兼容，但Agent不得用省略参数绕过本页访谈规则。出现不同项目或旧目标侧车时明确报数据不一致，不套用别人的需求。

下游HTML Skill先读需求侧车或对话中明确的需求文件：把人数、使用习惯、保留物、优先级用于功能区/锚点；把已明确的风格用于CMF；未知项保留，回问只针对新增实质缺口。模型、机位、原生渲染与方案册共享这份需求，不各写第二份客户画像。几何字段仍以共享layout schema为唯一源，不把访谈字段塞进墙/家具坐标。

空间连接需求要在布局前问清：阳台/厨房是敞开、半开放还是有门；平开或移门、常开/常关、透明或磨砂；门后为哪一个空间；外窗看到户外还是公共区；用户是否强调吊灯、吊顶、地毯或餐桌台面。只问资料中缺少的关键项，已知的不重问；未知和设计推荐分开记录，再落实到布局opening及cameraComposition字段。

# 设备外置运行配置

本包在 Ubuntu、Windows 来酷和 Genmachine 使用同一份业务代码。Python 3.10+、Node、Chrome/Edge、中文字体及依赖由本机设计 runtime 配置提供；优先用设备登记的 interior-python 包装入口。普通任务不临时安装软件。所有输入和交付保存在当前设备当前工作区。

HTML 和截图共享 interior-html-modeling/scripts/engine。纯 HTML 离线打开不需要 Python；编译依赖 jsonschema、shapely、numpy，截图使用 Playwright 和 INTERIOR_CHROMIUM 指定的浏览器。资源盒由本机包装器沿用，任务结束只关闭本次浏览器。依赖列表见正式 scripts 中的 requirements 文件。

平台凭据通过设备既有 IDK_ENV_FILE 或私有 .runtime 链接提供，分发包不包含凭据；不得跨设备复制登录态。原生绘图使用当前宿主实际提供的绘图工具，准备文件不等于生成图片。
